**Azure SPI Fieldnotes — product, learning, and editorial review**

Reviewed 12 September 2026: [published site](https://danielscholl-osdu.github.io/osdu-spi-training/), local training commit `92aac43`. The published JS and CSS asset names match the production build from this checkout. This is a new review; earlier reviews and supplied artifacts are unchanged.

The site has a useful instructional core: follow a partition request into its Azure provider, then follow a provider change through the fork and back into a stack. I would preserve that sequence, the visual design, and the optional exploration. The next iteration should concentrate on editing and presentation. The material repeatedly explains its own structure, and the recordings introduce theatrical language and factual corrections that make the subject harder to trust and remember.

The strongest passages already sound like an experienced engineer explaining something they have operated. They name the resource, the action, and the consequence. Use those passages as the voice standard for the rest of the site.

**1. What is working and should survive the next pass**

- **The running example earns its place.** `opendes`, `dev1`, `getPartition`, the cache exception, and the Table Storage fallback are specific enough to follow. The provider source confirms the essential behavior: `safeGet` catches a cache exception and returns null; `getPartition` then reads the table. A cache failure has a concrete consequence the learner can understand. [Provider implementation](/Users/danielscholl/source/spi-workspace/osdu-spi-partition/provider/partition-azure/src/main/java/org/opengroup/osdu/partition/provider/azure/service/PartitionServiceImpl.java:105).
- **The stack map gets the important geometry right.** Azure data resources sit beside AKS; the workstation and source repositories are outside the deployed environment. Reusing that map during creation lets the learner recognize what has changed. This is more useful than introducing a different architecture picture in every chapter. [Architecture renderer](/Users/danielscholl/source/spi-workspace/training/src/components/architecture.js:14).
- **The ownership table is the best interaction.** Paths as rows and branches as columns directly answer where code belongs. The deletion toggle demonstrates why upstream removal leaves the fork-owned provider intact. I verified that the visible cells and their accessible names change together. Keep the local before/after strip.
- **The handshake makes deployment observable.** Showing the lock, pod digest, run ownership, verification, and restore gives the workflow a visible result. The phone explanation repeats the changed lock and pod state where it can be read. The conditional restore case is especially valuable.
- **The operational distinctions are worth teaching.** CLI exit versus readiness; authentication versus authorization; build results versus API evidence; Git fetching versus reconciliation; and successful cleanup versus actual environment state are all good material for this audience. These contrasts address real misunderstandings and should remain.
- **The visual direction is coherent.** Restrained colors, clear borders, source paths, and the orange ownership treatment help the maps feel like engineering material. The native diagrams are stronger learning assets than the decorative generated posters.
- **The media controls support exploration.** A cue plays in place, the player persists, source notes appear with the selected cue, and timestamp history works. The video and audio pause each other. These interaction choices are useful even if the narration is rewritten.
- **The implementation is proportionate.** Plain JavaScript modules, separated content files, a shared architecture renderer, and content-integrity checks are a reasonable foundation. There is no obvious need for a framework migration to make the recommended improvements.

**2. The highest-value improvement: a more natural engineering voice**

The main AI-associated patterns are repetition, inflated stakes, staged agreement, and a preference for elegant formulas over direct descriptions. Individual short headings are fine. The cumulative effect of nearly every topic becoming “one thing, several things” or “a relationship, not a snapshot” makes the writing feel manufactured.

On the start page, the introduction and the “Where to begin” panel both describe following a request down and a fix back. The page then explains the frame, the path, the round trip, two reasons to visit, three meanings, six places, supplements, and documentation sets. Each section makes sense alone, but together they keep restarting the introduction. [Start-page renderer](/Users/danielscholl/source/spi-workspace/training/src/components/pages.js:102).

The narration is much more conspicuous. The orientation opens with a community garden, changes to a flooded skyscraper, and then introduces the episode. Its first 72 seconds establish atmosphere before naming the specific material. Later passages describe an eviction, a divorce, an orphan, and a custody arrangement. The transcript contains 14 uses of “massive” and 16 standalone instances of “exactly.” Those counts are clues to repetition, not quality scores. [Orientation transcript](/Users/danielscholl/source/spi-workspace/training/src/content/transcripts/orientation.js:3).

The tone also changes the technical story. “Handed their walking papers” suggests an adversarial decision; “the Azure directories literally no longer exist upstream” turns a planned removal into a completed event. The site's own source notes correct the governance framing, the public code's description as proprietary, and the removal timeline. A learner should hear the accurate account in the primary explanation. Source notes are useful for qualifications, but should not have to reverse the central story. [Existing narration checks](/Users/danielscholl/source/spi-workspace/training/src/content/audio.js:1), [upstream-filter decision](/Users/danielscholl/source/spi-workspace/osdu-spi/doc/src/adr/038-upstream-filter-transform.md:15).

The two-minute brief needs attention first because it is the introductory cue. It expands SPI incorrectly and ends with a generic promotional sentence about connecting innovation to cloud reality. Correcting the expansion only in a note leaves the listener hearing the wrong definition. Rewrite the brief from an approved script and produce matching audio and captions/transcript. Do not silently rewrite a transcript so it no longer represents its recording. [Brief transcript](/Users/danielscholl/source/spi-workspace/training/src/content/transcripts/brief.js:3).

**A possible opening for a replacement brief**

> OSDU services separate shared application code from cloud-specific implementations. The Service Provider Interface, or SPI, connects the two inside each service.
>
> The community plans to remove its Azure implementations from the shared repositories. Microsoft maintains the Azure provider in service forks and brings upstream changes into the shared code through scheduled workflows.
>
> Two projects support that work. osdu-spi supplies the fork workflows. osdu-spi-stack creates a development and test environment on Azure.
>
> This guide follows a partition lookup for opendes. You'll see where it runs, how the provider reads stored configuration when its cache fails, and where a provider change belongs. Later views show how an eligible workflow tests a candidate image in a stack and restores the canonical image while it still owns the pin. That acceptance run is illustrative; the reference partition fork has not adopted the newer workflow yet.

This gives the recording a concrete subject immediately. A single narrator would suit it well; two speakers can also work if one asks real engineering questions and the other answers them without staged surprise or repeated agreement.

The start page contains approximately 1,569 whitespace-delimited words in its rendered main content. That is a substantial introduction before the chapters. The primary desktop CTA is available early, so this is not a claim that everyone must scroll the whole page; the problem is the amount of competing framing, especially on a phone.

Keep one opening promise and put its action directly beneath it. A possible body is: “Follow a partition lookup through the Azure stack, then follow a provider change through its service fork and back into the environment. Each view explains one part of that journey and links to the source documentation.” The existing audience line can remain above it. Remove the second explanation of the same journey from “Where to begin.”

Keep the introductory media on the start page, but present it as a compact optional choice. The portrait video currently makes its desktop container much taller than the adjacent text requires. Put the ordered path before an expanded media treatment, or make the media block compact enough that it does not postpone the path. The three meanings of SPI and six-place reference can remain below the path, as the site's design intends.

On the path cards, use a short question or outcome rather than both a question and a full chapter conclusion. Some cards currently introduce detailed Maven, branch, provider, or image-lock information before the reader has opened that chapter. The card's job is to help someone choose and orient, not teach the whole chapter.

**4. Make the selected component answer the learner's immediate question**

View 03 promises to explain what happens when the partition cache is down. Its default Azure implementation selection instead opens “Azure source is seeded once and maintained in the fork,” followed by ADR-038 and repository ownership. Those are relevant facts for view 04, but the selected component in view 03 should first explain runtime behavior. [Current explanation](/Users/danielscholl/source/spi-workspace/training/src/content/component-details.js:272).

Suggested first explanation: “The partition provider checks its cache for opendes. If the cache misses or throws, it reads the stored configuration from Table Storage in common Storage. Cache failures are logged, so this lookup can still succeed.” Add the actual method or source link, then one short ownership sentence if needed.

There is a similar mismatch at the end of the lookup in view 01: selecting stored configuration opens a shared-data panel led by “Entitlements uses the shared Gremlin backend.” The panel eventually explains common Storage, but the learner has to find the answer to the component they selected. Put the partition configuration first in the request scene. Scene-specific lead text can preserve the shared component model without forcing the same introduction into every context.

Source references also need to support the selected claim. The cache-fallback explanation links to the upstream ownership ADR, which does not document that Java behavior. Keep that ADR for source ownership and add a direct link to `PartitionServiceImpl` and its regression tests for the fallback. Existing tests establish that a source key resolves; they do not establish that it substantiates the paragraph.

The “One request, end to end” poster beside view 03 follows a storage record read through to Cosmos DB. Its notes correctly distinguish that request from the partition lookup, but the compact inline poster does not carry that clarification. Add “Different example: a storage record read” beside the inline image, or use a partition-specific visual there. The learner should not have to leave the chapter to find out why its request suddenly appears to reach Cosmos. **6. Mobile, navigation, and reference material**

All ten routes inspected fit horizontally at 390 px. The ownership cards retain branch labels, and the restore panel exposes its state and can be dismissed with Escape. These are meaningful successes. The remaining mobile problem is reading and navigation effort: tall maps, a persistent header, the explanation sheet, and sometimes the player compete for a small screen. Branch identifiers also wrap into awkward fragments in the four-cell phone layout.

Prefer shorter component explanations with an immediately visible operational fact and optional detail. Keep the current ability to explore the complete map. Do not shrink type further to make the maps fit. The [phone restore screenshot](/Users/danielscholl/source/spi-workspace/training/output/playwright/390-restore-and-dock.png) shows how much screen space the combined controls occupy.

There is a reproducible keyboard problem. Focus the chapter-02 link in the desktop rail and press Enter. After the chapter renders, focus is on `BODY`; the next Tab returns to “Start here” in the rail. The chapter-navigation markup is replaced without moving focus into the new chapter. Add a skip-to-content link and a deliberate chapter focus destination. Keep the existing focus preservation for same-chapter lifecycle controls. [Navigation rendering](/Users/danielscholl/source/spi-workspace/training/src/main.js:124).

The Field guides page is an archive-sized page presented as a reading sequence. It starts with supplied posters and puts the native guides after them. Add a compact index organized by the reader's need—deployment, identity, provider code, fork maintenance—and lead with the current native material. The supplied generated posters contain obvious artifacts such as “CITOPS LOCK-FILE,” misspelled labels, and implausibly tidy timing claims. Their correction captions are responsible, but showing the large image first still gives the incorrect wording visual authority. Preserve the originals, distinguish them clearly as supplied references, and make the corrected native material the default teaching surface.

View 06 should provide a more definite stopping point. View 07 is a useful reference collection, but the sequence then continues to “Next: Listen.” That can make optional material feel like unfinished coursework. Close the request/change journey explicitly, then offer misconceptions, recordings, and source documentation as choices. Keep the learning experience free of quizzes, scores, or completion tracking.

For a learner who has never brought up a stack, views 01 and 02 would benefit from one compact worked example of the handoff to actual documentation: required access, the command sequence, an annotated readiness result, and the API endpoint to inspect. Keep it illustrative and optional. The current commands are useful, but distributed among selections and guide links; “Views 01 and 02 are enough” promises more practical completeness than their current presentation consistently provides.

**7. Suggested next iteration**

1. Edit the start page and chapter introductions for repeated framing. Keep the existing visual design and ordered path.
2. Replace the introductory brief with an approved, fact-checked script; revise the orientation's title and narrative before giving it a prominent introductory role. Preserve original reference media separately.
3. Correct the stale-pin wording, job-ID example, source-card implication, and authored poster takeaways. Make view 03's component explanations answer the request path and link to its real implementation.
4. Fix chapter keyboard focus and add a reference index. Check the same desktop/phone interactions after these changes.
5. Observe three to five engineers unfamiliar with SPI using the site. Watch where they stop, which labels they misunderstand, and whether they can locate a provider change or an environment failure. This is a product review session, not a learner assessment. Use the results to decide whether any further content is needed.

I would judge that pass by whether someone can enter quickly, follow the request without switching examples accidentally, understand which repository owns a change, and read the relevant evidence from the handshake. Additional chapters or recordings have less immediate value than making those existing experiences easier to follow.
