# Fieldnote 05 · A day in the fork

**Status: published.** Cut from lesson 05 (`chapters['fork-day']`). Revised against osdu-spi `main` 8935867, osdu-spi-partition `main` 8aa26ca0, and osdu-spi-stack `main` 870f729 (v0.32.0), and checked against the partition fork's public pages on 22 October 2026. Aim for about 3 minutes; the cut runs 3:15.

**Who is watching:** an engineer who has seen the fork's three branches in Fieldnote 04. **What they should believe after it:** upstream arrives as a generated tree through a reviewed PR, never as a merge someone runs, and it never carries the Azure provider; the tracking issue's labels are the state of the day; and every eligible commit gets an image digest and a turn in the stack before any release exists, so a release only tags an image that is already there.

**What changed since the first draft.** Since osdu-spi-stack 0.30.0 every service runs its Azure fork's `main` image from GHCR by default, and thirteen service forks carry a descriptor. So "a turn in the stack" is no longer a visit to a stack that otherwise runs someone else's image: each fork borrows its own service's slot, among thirteen, and the image a merge to `main` pushes is the one that slot follows next. And upstream no longer carries the Azure provider at all, so the fork is where the Azure code lives and a sync never touches it. The narration says both as the settled state, with no dates.

**The form is mixed: boards and GitHub footage.** Footage is the public pages of `Azure/osdu-spi-partition`, captured signed out in headless Chrome at 1920 by 1080 just after midnight UTC on 23 October 2026, the morning after one upstream change went through the whole pipeline: the scheduled Sync Upstream runs, sync PR #200 into `fork_upstream` and its generated commit, tracking issue #201 and its labels, integration PR #202 into `main` and the open version PR #198, the Validation run on the merge to `main`, and the container package's tags. Each crop is the element that matters, never the full page. Boards follow the lesson's figure, "The branches, in time", as five moments. Lesson 05's outcomes are plain sentences, so its chapters are titled with the sentences.

**The scene:** the three branch columns from Fieldnote 04 turn on their side into three lanes on a time axis, midnight at the left. Upstream sits above the lanes, outside them. The stack appears only at the fourth moment, as the image lock with one row per service fork. Fork-owned changes are orange. ## The day the footage shows

Sync Upstream started at 00:30 UTC on 22 October (its cron is midnight; GitHub starts scheduled runs late) and opened sync PR #200 and tracking issue #201. A person merged #200 at 17:24 UTC. Cascade Monitor, which also runs whenever a PR into `fork_upstream` closes, dispatched the cascade 22 seconds later; the cascade opened #202 at 17:26 and labeled #201 `validated`. A person approved #202, its armed auto-merge landed at 17:59, and Validation on that push pushed `sha-8aa26ca007ad`, moved `main-snapshot` to it, and ran Deploy and Test against the shared environment. Release Please's version PR #198 for 1.3.4 is still open; the last release, 1.3.3 on 20 October, tagged the image already pushed as `sha-544a15d4a811`.

Upstream's partition repository removed its Azure provider and Azure CI/CD on 20 October (`a2c4f7b7`), and legal, schema and file followed. The narration states the result, not the event.

## Word list the narration must keep

- Times on the axis are the workflows' scheduled triggers, not measurements. Only the midnight sync is named. A time in footage is what the page shows.
- Upstream doesn't carry the Azure provider; the fork does. Say it in the present tense, with no dates, no "plans to", and no list of services.
- Upstream is never merged as text. The only merges are the cascade's into `fork_integration` and the reviewed PRs.
- The cascade order is `main` first, then `fork_upstream`. The narration doesn't say who starts the cascade.
- Validation pushes a digest for every eligible commit; "eligible" stays in the narration.
- Thirteen service forks carry a descriptor, and each borrows only its own service's slot. The episode follows partition and says the count once.
- The stack follows each fork's `main` (the `main-snapshot` tag); it never resolves a version tag. "The one that slot follows next" is as far as the narration goes: when the slot moves is Fieldnote 08's subject.
- The release is optional and tags an image that already exists. Release Please opens the version PR; the episode does not explain Release Please further.
- Template sync and Settings Apply run on their own clocks and stay off screen.
- The cache fix and its unit tests are real; the acceptance run is illustrative. Say both, once. The 22 October run in the footage is real, and is not the cache fix's run.
