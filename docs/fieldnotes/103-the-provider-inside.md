# Fieldnote 103 · The provider inside

**Status: published.** Level 100, the third foundation episode. Its companion page is `chapters['spi-boundary']`, and its cut-from record is in `src/content/videos.js`.

**Who is watching:** anyone taking the course, straight after 102. **What they should believe after it:** the Azure code is a provider behind a Java interface inside each service, not a separate service; shared code and provider ship in one image, so crossing the interface is a method call; and the provider is source in the service's fork.

## Word list the narration must keep

- The SPI here is the interface inside one service, the second of the three meanings 101 named. Say "Service Provider Interface" once.
- No network hop between the interface and the implementation. Redis and Table Storage are network dependencies; the interface is not.
- The community implementation is named, not opened, and it is not in the fork: the fork carries `partition-core/` and `provider/partition-azure/` only.
- The provider lives in the fork, in the present tense. No upstream history, removal, or dates.
- The lookup reads stored configuration from common Table Storage after a cache miss and does not visit the partition's Cosmos DB, blob Storage, or Service Bus.
- No code, flags, or commands on screen.
