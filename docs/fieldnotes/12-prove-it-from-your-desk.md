**Status: storyboard draft, written after the take.** Season 2, _Working the stack_. Cut from osdu-spi-stack ADR-036 (`docs/decisions/036-spi-test-runs-the-deployed-commit.md`), ADR-037 (`docs/decisions/037-spi-test-reports-what-a-suite-proves.md`), ADR-038 (`docs/decisions/038-local-builds-pin-from-the-environment-registry.md`), PRs #279, #285 and #297, `src/spi/testing.py`, `src/spi/suite_report.py` and `src/spi/build.py`, read at `main` 870f729 (identical to the v0.32.0 tag 3d3106d outside `ops/`); `Azure/osdu-spi-partition` at `main` 8aa26ca0, the commit the take deployed; and the 22 October take on spi 0.32.0. The lesson it proposes is `prove-from-desk` in the _Working the stack_ book.

**Who is watching:** an engineer with a Deployable environment (Fieldnote 10) who has read which commit each service runs (Fieldnote 08) and will change a service fork. **What they should believe after it:** `spi test <service>` runs the suite that the deployed commit itself shipped, against that environment; a pass counts tests, and `--report` and `--review` are how you learn what those tests prove; and a change on their own machine reaches the environment as a local pin they can test the same way.

**Money shot:** the report page's header, `8aa26ca007ad`, set beside partition's `sha-8aa26ca0` row from Fieldnote 08's `spi info`: the suite and the service from one commit.

**Form: footage-led.** One `spi test partition --report` run and the two pages it wrote carry claims 1 and 2 and the example. Claim 3, the local build and pin, was not recorded on the take, so it is drawn and labeled. The easy mistake uses real source from the deployed commit, not a drawn failure.

**Length:** about 4 minutes (estimate below).

## Keep it true

- Paired mode is the default: the suite image is the lock's repository plus `-acceptance`, pulled for `linux/amd64` by the digest recorded when the canonical was resolved (`<SERVICE>_ACCEPTANCE_DIGEST`). The pair promises the commit, not the build. A pin, a non-canonical entry, or no recorded digest refuses with `unpaired`.
- The CLI never reads the descriptor itself. It fetches `.spi/service.yaml`, the acceptance resolver and `suite-verdict.py` from the service's repository at the full commit, and runs the resolver with facts from `spi info`.
- Guards before, check after: the run refuses while not Deployable or while an ephemeral pin borrows the service, and discards the result as `target_changed` if the lock entry, the rollout revision, or a pod's digest changed during the run. `spi test` holds no lease.
- The verdict is the commit's `suite-verdict.py`: a zero exit, at least one test not skipped, no failures or errors. Exit codes 0, 3, 2, 1. Say "the commit's own verdict", never "the CLI decides".
- The CLI mints the deploy, member and no-access callers through the path `spi token` uses; an identity the environment does not provision leaves its variable unset. Do not say which caller a given test uses.
- `--report` computes facts (status, duration, `empty`) and sends nothing anywhere. `--review` sends the suites' sources and the run's facts to a reviewer (`copilot -p`) and grades against the service's own `api-docs`. Neither changes a verdict or an exit code. The take's scoreboard says `not reviewed`.
- `empty` means a passing test whose body, in the suite's own sources, holds no statement. A test inherited from outside the suite is `outside`, not empty. The skipped `should_returnExpectedRevision` is inherited from a base class outside the suite; do not explain why it skipped.
- Hollow tests exist: at `8aa26ca0`, partition's `integration` suite (`testing/partition-test-azure`) overrides fifteen 401 tests, three in each of five classes, with an empty body and `// revisit this later -- Istio is changing the response code`. That is the evidence behind the myth, and it stays off screen and out of the narration: it is a defect someone will fix, and the take never ran that suite. Never say the take's run had empty or hollow tests.
- Hollow is the empty tests plus the passing tests a review graded 0 on every row that cites them. Without `--review`, Hollow counts only the empty ones, so the take's `0` says no test was empty, not that every test proved something.
- `spi build` and `spi service pin --source` build the JAR on the host (`clean install -P core,azure -DskipTests`) and the image with `az acr run` for `linux/amd64` into `<registry>/local/<service>`, tagged `sha-<12>`, `-dirty` or `-prebuilt`, pinned by digest with origin `local`. A local pin refuses while the service is borrowed. `matched` needs the pinned commit and a clean tree.
- Paired mode on Apple Silicon runs under emulation; checkout mode needs a JDK and Maven, paired mode needs Docker. Neither is part of `spi check`.
- `spi test dags` is Fieldnote 11's; this episode never shows it.

## Proposed lesson

`prove-from-desk`, in the _Working the stack_ book, last. Map lesson that uses both of lesson 06's maps at once: the fork repository on GitHub on one side, and your environment's image lock, pod, and registry on the other, with the workstation between them.

- **Title:** Prove it from your desk
- **Subhead:** spi test runs the suite the deployed commit shipped, the report says what its tests prove, and a local build reaches the environment as a pin you can test the same way.
- **Question:** How do you prove a service from your desk?
- **Builds on:** the image lock and the borrow from lesson 06, and the canonical images from `whose-image`.
- **Outcomes (headlines):**
  1. spi test runs the suite the deployed commit shipped.
  2. A pass counts tests, and the report shows what they prove.
  3. A change on your desk reaches the stack as a local pin.
- **Example:** _spi test partition, paired_, `spi test partition --report`. Hops: guards (Deployable, not borrowed, target read before) → image lock (`sha-8aa26ca007ad` and the recorded acceptance digest) → GitHub at the full commit (descriptor, resolver, verdict script) → paired image (`docker run`, `linux/amd64`, by digest) → verdict and page (the commit's verdict; target read again; `spi-test-partition-acceptance.html`).
- **Easy mistake:** `passed-means-checked`, owner `fork`, theme `seam`. Claim: "The suite passed, so every test checked something." Reality: the verdict counts tests, and JUnit reports a test with an empty body as a pass. The report's Hollow column counts the passing tests that prove nothing: the empty ones `--report` finds in the suite's sources, and the ones `--review` grades as proving nothing against the service's own API contract. Without a review, Hollow counts only the empty ones, and the scoreboard marks the service `not reviewed`. Correction: "A passing suite can hold tests that prove nothing; the report's Hollow count, with --review, says how many." Check: `spi test partition --suite all --report --review`. Sources: new keys for ADR-036 and ADR-037.
