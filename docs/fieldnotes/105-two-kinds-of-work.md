**Status: published.** Level 100, the fifth and last foundation episode. Its companion page is `chapters['two-kinds-of-work']`, and its cut-from record is in `src/content/videos.js`.

**Who is watching:** anyone taking the course, straight after 104. **What they should believe after it:** the line (the template and its workflows, the shared stack, and the automation that runs them) carries the product (each service's code, its Azure provider, its tests, and what it promises its callers); automation opens much of the work, and nothing reaches main until a code owner approves it after its last push with the required checks green; and the work a person does, changing a service or changing what carries every service, picks their path.

**The scene:** each beat is a concept scene drawn in vector motion, in the site's colors and fonts, with something always moving. No scene shows the site's interface, a map drawing, GitHub footage, or a command. Everything stays at level 100: one line, one service card, one gate.

Its numbers (pull request counts, queue sizes, fork counts, dates) stay out. All narration is new. Labels, the tracking issue, the checks' names, and footage stay out: S206 reads a pull request's checks, S207 the labels a change carries, and P204 the day's workflows.

## Word list the narration must keep

- No role names. Builder and Steward never appear; the paths name kinds of work, not job titles.
- No agent model. Charters, the autonomy ladder, the line board, and named agents are not documented in `osdu-spi`. Copilot appears by name only as a reviewer whose review is not the approval.
- "Nothing reaches main until a code owner approves it." The default-branch ruleset has no bypass actors, requires a code owner's review, one approval, approval after the last push, and the CodeQL and Validation Summary checks with the branch up to date (`osdu-spi` `.github/rulesets/default-branch.json`). Cascade arms auto-merge, which waits for that approval (`.github/template-workflows/cascade.yml`), so the narration never says automation never merges.
- "Copilot may review a pull request first." Copilot reviews pull requests to main where the organization supports it (`doc/src/architecture/overview.md`), and a Copilot review is never an approval. Never "every pull request gets a review".
- The checks are "the required checks". Their names and what each proves are S206's.
- "Opens an issue for a person": a halted sync or a cascade conflict opens an issue marked for a person. The label's name and its retry are S207's and S305's.
- A person merges the sync pull request, approves cascade's pull request into main, and merges the release pull request "when the version and changelog are ready" (`doc/src/workflows/release.md`). Never "once nothing is open".
- No fork count, pull request counts, queue sizes, or dates. No branch names but main, no labels, no version numbers, and no commands on screen.
- The lane is not drawn in this episode; 104 placed it, before any release.
- Orange appears only on the service card's Azure provider row. A person mark uses the site's "you" slate; the line stays blue. Green and purple are owner colors on the site's maps, so the two kinds of work do not use them.
