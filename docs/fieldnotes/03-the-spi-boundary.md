# Fieldnote 03 · The SPI boundary

**Status: draft for approval.** Cut from lesson 03 (`chapters['spi-boundary']`). Aim for about 2 minutes 20 seconds, the length of Fieldnote 01.

**Who is watching:** an engineer who knows OSDU and has just opened lesson 03. **What they should believe after it:** the Azure code is a provider behind a Java interface inside the partition service, not a separate service; shared code and provider ship in one image, so crossing the interface is a method call; and the fork keeps that provider apart from the shared code it regenerates.

## Word list the narration must keep

- The SPI here is the interface inside one service, the second of the three meanings on Start. It is not the stack and not the engineering system.
- No network hop between the interface and the implementation. Redis and Table Storage are network dependencies; the interface is not.
- The lookup reads stored configuration in common Table Storage and does not touch the partition's Cosmos DB, blob Storage, or Service Bus.
- Cache down assumes common Table Storage is reachable and holds `opendes`. Never say the provider survives a Table Storage failure or a missing partition.
- Claim 3 says "generated" and "fork-owned" only. Branches, the filter, and how regeneration runs belong to Fieldnote 04; the cache fix's history belongs to 04 and 05. This episode shows the behavior on `main`, not where it came from.
- Upstream _plans_ to remove its Azure implementations. Never say it already has.
- The community implementation is named, not opened: its cache and PostgreSQL stay in the lesson's comparison.
- The optional image check from Try it is not boarded; an image reference does not prove which source built it.
