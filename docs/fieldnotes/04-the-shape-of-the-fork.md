# Fieldnote 04 · The shape of the fork

**Status: revised 22 October 2026; in production.** Cut from lesson 04 (`chapters['fork-shape']`). Aim for about 3 minutes. The revision follows two changes since the first draft: upstream removed partition's Azure provider on 20 October 2026, and thirteen service forks now share the reference fork's shape (osdu-spi-stack 0.30.0 runs each one's `main` image by default). The three outcome sentences, the example, and the myth are unchanged.

**Who is watching:** an engineer who has just seen the Azure provider inside the partition service in Fieldnote 03. **What they should believe after it:** the fork owns a short list of paths and everything else is regenerated from upstream every day; three branches have three jobs; and the generated branch never carries the Azure paths, so an upstream deletion has nothing to delete, as the real one on 20 October showed.

**The form is mixed: boards and GitHub footage.** Footage is captured from the public pages of `Azure/osdu-spi-partition` on the day of the cut: the root listing on `main`, the branch list, the `provider/` folder on two branches, upstream's deletion commit as it appears in the fork's history, the generated commit that followed it, and the latest generated commit's trailers. Boards explain the ownership grid the footage can only hint at. Lesson 04's outcomes are plain sentences, so its chapters are titled with the sentences, as the site does today; per-claim cues arrive when the lesson moves to the claim grammar.

**The scene:** the lesson's figure, "One repository, read by owner", built as a vector grid: paths as rows, the three branches as columns, cells that say where each path exists. Fork-owned rows are orange; upstream's rows are ink. Upstream sits outside the grid. Footage sits in a browser pane on the sheet, cropped to the element that matters, never a full-page screenshot. The recall is drawn: three notebook panels in the series' linework, with the outcomes set in type.

## Word list the narration must keep

- `fork_upstream` and `fork_integration` are spoken "fork upstream" and "fork integration".
- The example is illustrative from its first hop: the real cache fix arrived from upstream before the filter existed. The narration says so once, at the start.
- The fork owns paths, not the repository. Never say the fork "owns the code" without the path.
- Upstream _has begun_ removing its Azure code. The community partition repository deleted `provider/partition-azure` and its Azure tests on 20 October 2026; legal's went the same day and schema's and file's on 22 October. Never say every service's Azure code is gone.
- `osdu-spi-partition` is the reference fork. As of 22 October 2026, thirteen service forks under the Azure organization (crs-catalog, crs-conversion, entitlements, file, indexer, indexer-queue, legal, partition, schema, search, storage, unit, workflow) each carry the three branches and a descriptor, and none has `provider/` on `fork_upstream`. The episode names the count once and follows partition; it does not claim the others own the same paths, since a service laid out differently lists its own fork-owned trees.
- Since osdu-spi-stack 0.30.0, every service's default image is its fork's `main` build on GHCR. Say "by default": an environment can record a trusted mirror instead. Image refresh and age belong to Fieldnote 08.
- The nightly sync generates the new tree as a commit and proposes it to `fork_upstream` in a sync pull request, so the branch's tip is that pull request's merge. The trailer check searches for the generated commit rather than reading the tip.
- Mirror forks and the sync and cascade mechanics belong to Fieldnote 05.
