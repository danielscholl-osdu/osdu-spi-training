OSDU SPI Stack · The shared environment as built

The Backing Environment

One standing stack, pinned to a reviewed release tag, backs every fork's deploy and test lane

The rule
The stack definition moves only by a reviewed bump PR, never a rolling branch.
one bad merge on a branch would stop every fork's merge gate at once
Chassis · one ordinary stack, spi up --env <name> --profile core --tag vX.Y.Z · its version is three axes, not one
Axis 1 · stack definition
pinned
Manifests, charts, and the CLI at one release tag
Declared by stackVersion in ops/environments/<name>.yaml. Flux fetches the tag; the workflows install that release's wheel, so the executing CLI and the Flux ref name the same commit. A ruleset forbids moving a v* tag.
moves by: bump PR merged → env-upgrade
Axis 2 · canonical images
recorded
The service digests in osdu-image-lock
Every canonical image comes from the community registry today. The weekday refresh preserves them; only an upgrade's --refresh-images pass moves them, after a lock snapshot is saved as a run artifact.
moves by: env-upgrade only
Axis 3 · ephemeral pins
transient
A fork run's image under test, one service at a time
spi service pin --ephemeral writes the digest and the owning run id; reset --if-run puts the canonical back. Siblings keep serving; spi status --json lists the pinned services.
moves by: the fork's deploy-test job
How the pin moves · release to running upgrade
Release
1
release-please publishes vX.Y.Z · a job opens the stackVersion bump PR under the release App token
Review
2
a human merges the bump · the push to the pin file is the trigger · nothing else moves this axis
Upgrade
3
env-upgrade: set maintenance, snapshot the lock, spi up --tag --refresh-images with the tag's own wheel · 6 h budget
Open
4
source resumed, revision checked against the tag's commit, suspended again · probes pass · the flag clears and forks may deploy
Refresh, built: env-refresh on weekdays at 05:00 UTC sets maintenance, runs plain spi reconcile, waits for Flux and the gateway probes, asserts the deployed ref and source suspension are unchanged, then clears the flag. It moves no axis. A red run leaves the flag set.
What deployable means
ready
every gating Kustomization reports Ready=True · seeding work never flips it · the lifecycle jobs read this while maintenance is set
deployable
ready, and maintenance unset, and a deploy record present, and the entitlements-members Job Complete for every partition
reason
one typed blocker when false: a non-ready Kustomization, the flag, a missing record, bootstrap_failed or bootstrap_pending
exit
0 deployable · 2 not, with the reason · 1 unreachable or guard failure
Fails closed. A failed upgrade or refresh keeps the flag set, so forks wait with a reason instead of racing a half-changed platform. A fork polls this for up to 10 min before borrowing.
The reset boundary · spi down is built
spi down keeps
The resource group, its tags (name suffix, source policy, declaration locator), and the managed identities: the deploy identity and its federated credentials survive, so every fork's five values stay valid. 45 min deadline; success only once the group holds identities alone.
spi down --purge deletes
The group and its identities, after removing the ExternalDNS zone grant it discovers from the retained principal ids. An unrecognized grant leaves everything standing.
