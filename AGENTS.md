# OSDU Fieldnotes training site

This repository owns the learning site. Keep its files separate from `osdu-spi`, `osdu-spi-stack`, and service forks.

## Product intent

- The audience is senior engineers who know OSDU but are new to SPI, the Azure stack, and the fork engineering workflow. Do not assume they can already bring up a stack.
- Teach through architecture, visual progression, and optional exploration. Avoid learner quizzes, scores, required exercises, or completion tracking. Development checks are separate from the learner experience.
- Keep prose short and use documentation links for depth. Preserve the established visual direction while the prototype is being reviewed.
- Distinguish the workstation, Azure, the complete deployed stack, AKS, and the provider code inside each OSDU service.
- Examples are illustrative. The site must not execute Azure or SPI commands or imply it reports live environment state.
- The site publishes to GitHub Pages from `main`. Keep commits on `main` deployable; work on branches otherwise.

## Source and workflow

- Edit `src/`; `dist/` is generated build output and must not be committed.
- Chapter copy and navigation live in `src/content/chapters.js`; the zoom ladder and the three meanings of SPI live in `src/content/concepts.js`; explanations, creation moments, fork moments, audio markers, Fieldnotes (`videos.js`), field checks, and posters have separate files in that directory. Each learn chapter names its `book` (Foundations, The stack, The fork, The seam, Across the path, Working the stack); the rail groups by it. The start page's lesson index groups by the `index` on the start chapter. Page renderers live in `src/components/pages.js`; native field guides in `src/components/infographics.js`.
- Diagram markup and behavior live in `src/components/`; shared navigation and detail handling live in `src/main.js`, with URL state in `src/router.js`.
- Keep the vanilla JavaScript module structure. Add dependencies only for a concrete need.
- Use `npm ci`, `npm run dev`, and `npm run check`. Use `npm run format` after editing.
- Preserve a review server already in use. The development server defaults to `127.0.0.1:5173`, separate from the original review preview at port 8875.
- Ground technical changes in current `osdu-spi-stack` and `osdu-spi` source documentation. The supplied CIMPL infographics are visual references, not authority for Azure SPI behavior.

## Learning-content standards

- `src/content/course.js` numbers the pages, and the position line, pager, rail, and Start's index read their numbers from it; copy that names a page by its number is written by hand. The four Foundations pages (`running-stack`, `spi-boundary`, `the-line`, `two-kinds-of-work`) come first, and each shows its level 100 episode's code (102 to 105) and “Level 100 · N of 5”; Start is 101's page, so `running-stack` reads 2 of 5. The other lessons keep their numbers from the original twelve-lesson tour and their “Lesson N of 12” labels, so `bring-up` is still 02 and the fork lessons still 04 and 05 though they follow 105. Working the stack follows Across the path; `whose-image`, `who-is-asking`, `ready-not-loaded`, `core-dags`, and `prove-from-desk` are lessons 08 to 12, and the original field check remains 07 with its Back to the start exit. The last lesson, `prove-from-desk`, also ends with Back to the start. Start groups pages as Level 100 · Foundations (102 to 105), The stack (02), Provider code and engineering (04 to 06), Across the path (07), then Working the stack (08 to 12). Future entries in Working the stack follow storyboard order when published, without placeholders. Fieldnote IDs in `videos.js` are independent: Fieldnote 11 belongs to `core-dags`, and a Foundations page shows its episode's code because that episode's Fieldnote names the page as its `chapter`. A lesson may precede its recording; only produced media enters the manifest, and synthetic test fixtures are not publication evidence.
- Every component explanation must add a concrete operational fact and name an artifact, command, resource, number, or failure mode. Its source reference must resolve. Do not repeat the paragraph beside the map.
- Start from familiar OSDU APIs and partitions, then introduce the new SPI and environment boundaries. Explain the acronym once; do not assume prior SPI knowledge. Say which of the three meanings of SPI (the interface, the Stack, the engineering system) a sentence uses when it is not obvious.
- The map lessons each answer one stated question, name what they build on, say in one sentence which of the six places they work at, may carry an example as optional depth labeled “Example: …” (the original round trip follows a partition lookup for opendes, then a fix to the partition provider; core-dags follows ingestion; each hop selects a component), show one easy mistake from the myths directly under the map (keyed by moment where the map has moments) unless the lesson's Fieldnote is a curriculum episode that carries no myth, and end with two or three things the learner can now say. Lesson 07 remains a learn view but closes the original round trip as a field check. The question, goal, and example live in the content model for review; they are not each displayed as a separate row of interface text. Position on the ladder is stated in prose, not as a control: a chip strip was tried and read as navigation. New content must fit a place; if it does not, the ladder is wrong or the content belongs in a supplement.
- A map lesson follows one grammar, in this order: position line (“Lesson N of 12 · book” on a lesson, “Level 100 · N of 5” on a Foundations page), the lesson title as the H1 (the same words as the rail: a phrase with no punctuation, one color, never a sentence and never split across two tones), the standfirst under it (`subhead`: the sentence to remember, one full sentence with a full stop, set in the site blue the way Start's subhead is), one short lead that carries the concept in a sentence or two (not a question row, not a goal row, not a description of how the lesson works), “Watch this lesson” with the episode's length on every lesson that has a Fieldnote, an optional supporting paragraph after it, an optional premise line under both, one map workspace with its figure title, two to four claim selectors, the selected claim's explanation, and the map, optional evidence in the drawer, one easy mistake (none when the lesson's Fieldnote is a curriculum episode that carries no myth), “What you can now say” under a single heading, then the unchanged optional “Try it” band, then optional depth, then the pager at the page end: the position line, a quiet Previous, and a Next lesson card with the next lesson's title and question. There is no bar between the outcomes and Try it. Every map lesson consolidates that depth in one Go deeper shelf whose applicable rows are ordered Follow the example, Hear it explained, Field guides, Sources and start closed. Each row is a small badge drawn in the site's field-notes style (`src/components/badges.js`: a path through three owner-colored nodes, headphones with gear cups, a folded sheet with a magnifier, an open notebook), a bold title, and one short preview derived from the content (hop count and example title; excerpt count and minutes; diagram and poster counts; reference count). Titles and links appear only when a row is opened, and the play chips sit inside the opened audio row so every row has one action. The shelf, the scope caption under the figure, and the pager do not depend on the claim grammar; lessons 04 and 05 carry them today and gain claim selectors when their grammar is migrated. The claim count follows the content. Lesson 02 is the lifecycle exception: its stages occupy the primary workspace-control position, and its noninteractive claim statements follow the stage-driven workspace before the easy mistake. Lesson 06 is the run exception: its six steps occupy the primary workspace-control position as buttons, each moving the lock and the pod, focusing its component, and showing its line in place; its noninteractive claim statements follow the step-driven workspace before the easy mistake; “How we know →” is the only path from a step to the drawer; and its Go deeper shelf does not render Follow the example, because the steps are that control. Lesson 07 is the field-check exception: its seven themes show every quoted assumption and correction, then two chips per row before its optional disclosure: who to ask (`owner` in `myths.js`: CLI + Bicep, Flux, controllers, the operator, or the service fork, drawn in the owner color the maps use, with a legend of those colors at the top of the page) and which tool the check reads with (derived from the check command's first word, never authored separately), with each row's command and evidence links in the disclosure. It retains its theme backlinks, stable myth anchors, prerequisites, location, and outcomes. It is not a quiz, required exercise, or completion tracker.
- Every lesson shares one stacked header at every width: title, standfirst, lead, never side by side. A lesson sets `subhead`, not `headline`; `headline` belongs to Start, Audio deep dives, and Visual field guides, whose H1 is not the rail title. The lead is the first paragraph of `intro` (a plain string, or the first `<p>` when the intro has more than one) and stays under 160 characters; the rest of the intro is body copy under it; `premise`, where a lesson has one, is a short accent line after the intro, not a line above the headline.
- A claim has a short headline (the scannable control), a full sentence (carried into “What you can now say”), and a reason underneath. Keep the headline under about twelve words.
- “Try it” is the hands-on band: what to run or click to do what the lesson described, on the learner’s own personal GitHub account and Azure subscription. It is optional, collapsed to one line by default, expands in place without moving the page, opens no drawer, and stores nothing. Each band states its prerequisites and can be started once they are met; it links to shared setup rather than repeating it. Its collapsed banner shows a badge for the activity (`badge`: workstation, workstation-cloud, or code-magnifier), the title and qualifier from one short `summary` in the content (“Try it: bring up an environment · Azure charges apply”, split at the separator and prefixed Optional), and a one-sentence `outcome`; never a concatenation of variants and timings, and timing stays qualified inside the band. It sits on a pale blue ground with slightly more padding than the Go deeper rows. Walkthrough dates and status do not appear in the learner interface; the full tested record (CLI release, stack ref, template commit, shell, operating system, date) stays in the content as publication evidence and is not rendered. Expanded, it names the intended result, the access it needs (browser only; workstation setup; public GitHub repository; Azure resources billed separately), the prerequisites as chips (one per tool, lesson, access, or browser, each with a kind glyph, a short label, an optional clause, and its source link; a shell-specific chip switches with the shell picker, and a lesson chip links to that lesson), what it changes as a footprint of three places in a fixed order (your workstation, GitHub, Azure subscription), each stating untouched, read only, changed, or created and billed with a short note, followed by the effects sentence; then your time as one bar proportional to the planning minutes in the content (active solid, automated wait hatched, clean-up muted; a zero segment is omitted) with the three qualified statements as its legend, so the bar is decorative and the statements carry the claim; the steps (each a touch marker saying what the step does before its command or click: reads only, changes your workstation, creates, or removes, with a short clause, so a surprise such as a dry run creating the resource group is visible before the command; then what to look for), the common alternate result and what to do then (“if no PR appears, check whether the fork is already current”), the clean-up including an optional ledger of what each removal command keeps or removes and what remains afterwards, and the runbook or CLI help it quotes, linked on its repository's default branch (the revision it was walked against stays in the unrendered tested record). Emphasis in the band is by weight, not hue: created-and-billed and creates are solid navy, untouched is dashed and muted, and no owner color or orange is used, because the band names no owner. Placeholders in commands are marked and the shell is named. Only the running example’s partition name (`opendes`) and the marked placeholder `<name>` for the environment appear; the site names no environment, because each learner creates their own with `--name`. The site still executes nothing and shows no live state. Features documented ahead of the code (the stale-sweep workflow step, `env-reset`, `env-teardown`) are out of bounds, and a band ships only after someone has walked its route and recorded the tested CLI release, stack ref, template commit, shell, and date. A band never becomes required, scored, or tracked.
- Nothing required to satisfy “What you can now say” lives only in the drawer; the lesson must work with the drawer closed. A detail that answers “how do I prove, check, or debug this” belongs in the drawer; a detail that answers “what should I understand” belongs on the lesson surface. Apply this in review of every content change.
- In lessons with structured claims, the claim is the primary interaction and changes the map; selecting the already-selected claim leaves it selected and opens nothing. A claim that is a chapter of the lesson's Fieldnote carries a small cue with the chapter's time beside its selector; the cue opens the video at that chapter, and selecting the claim still changes only the map. Plain-sentence claims (lessons 04 and 05) have no selectors and so no cues. Only “How we know →” opens the drawer, on the claim’s evidence component. In a lifecycle lesson the stage is the primary interaction and the map, the stage explanation, and its evidence entry change together. Running-example hops are optional depth, collapsed until requested, and trace the path when selected.
- The evidence drawer is closed by default. It opens by intent: a component, hop, evidence link, explicit map jump, or a route with `?detail=`. It shows the component name, `<context> · <owner>` metadata when an explicit owner exists (context alone otherwise), then two unlabeled explanatory paragraphs; optional More detail, Verify it, and Sources follow. It overlays the desktop map and uses a bottom sheet below 760px. Close with × or Escape and return focus to the opener. Closing keeps the selected component, its highlight, and any map state it drives (lesson 06's lock and pod); selecting a claim, a stage, or another lesson clears it.
- There is no map mode toggle. In a lesson with claims, focused components stay at full weight and others recede but remain clickable; a claim about a container (scopes named, no focused components, such as the running-stack map's opening claim) lights its boundaries and recedes nothing, so nothing on the map reads as dimmed for no stated reason; receding is a background weight, never a disabled one; only the evidence component advertises “Inspect ↗”, and the others show it on hover or keyboard focus. On a device without hover, receded components stay readable. Boundaries never recede. Nothing on a map is reachable only through a mode.
- Keep the current lesson’s exit before optional depth. Audio cues keep the label “Hear it explained”. “Watch this lesson” is the lesson's own recording: its Fieldnote, narrated from its claims.
- Interaction rule: selecting an idea or stage produces a visible local result; opening media or evidence preserves the reading position; a control that navigates names its destination (“Show it on the map ↑” carries `data-map-jump`; “Continue to Use the stack →” brings that stage's explanation into view). Deliberate navigation may move the page and says so; nothing else does. A field guide beside the map explains in place; a supplied poster opens in the lightbox with its notes; the familiar-things rows open their explanation inline. An easy-mistake callout explains locally: it shows the same two chips as its lesson 07 row under the quoted claim, it carries no link to the whole collection, and its evidence link targets a component on the current map or explains in place rather than changing chapter.
- The running example's provider path is the partition service's real one: cache, then Azure Table Storage in common Storage, returning stored configuration. It does not visit the partition's Cosmos, blob Storage, or Service Bus; say so wherever the example reaches the provider.
- The six maps of the original tour are one round trip: down the stack (102, 02, and 103), out to the fork (04, 05), back in through the image lock (06). The line (104) and Two kinds of work (105) work where the code comes from, ahead of the fork lessons: the line every fork shares, and where a person acts on it. Lesson 06 hands off to lesson 07's field check, which remains in the index and rail. The fork has no place inside Azure; its map is the repository read by owner (rows are paths, columns are branches) and its lifecycle is a day of scheduled workflows. Keep the seam view sparse: the running example's hops are the prose, everything else lives inside a component.
- Each map draws only its rung of the ladder. The running-stack map (102) draws the osdu namespace as one closed node (“OSDU services · one image each”) and holds the Git and image source nodes for lesson 02, where they appear once Flux assembles the workloads; the SPI boundary (103) opens the service to show the shared code and the Azure provider. A page's third claim and its running example stay at that rung too, so 102 says the services run in one namespace behind one gateway and its example ends at the stored configuration without entering the service. Routes into a component drawn at a later rung resolve there through `retiredDetails`.
- The six places are not a pure nesting. The resource group holds the Azure data services and the cluster side by side; the cluster nests namespaces and services; the source feeds a service and is drawn outside the stack. Do not redraw the ladder as containment all the way down.
- The start page, Fieldnotes, Audio deep dives, and Visual field guides have no rail; the chapter rail belongs to lessons, where it shows position. Start leads with one promise: a headline that names the subject in one line without a full stop (“Understanding the Azure SPI machinery”; every H1 on the site is a title, and the sentence with a full stop is the subhead's job), a subheading under it saying what the machinery is (the stack, the provider inside each service, the engineering that keeps them current), then, side by side at desktop width so that together they span the same width as the cards below (the strip on the left, stacked first on a phone), the machinery strip (generated; its prompt lives in docs/reference/start/, and the web copy is cropped to the three gears so it stays compact and legible on a phone) and three short paragraphs that say how the parts work together: the stack and what it runs, the provider a service calls through the Service Provider Interface (SPI), the forks that keep that provider while taking upstream’s changes and the workflows that build and test; the last names the OSDU Community Implementation (CIMPL) with a link as the reference the lessons compare against. The subhead names the parts, the strip shows them, the paragraphs relate them; the opening does not explain the site’s naming convention (that is the three cards’ job) and does not list the parts again. The words “OSDU on Azure” do not appear on Start: that name belongs to the earlier GitLab-hosted implementation. Then “Introduction” with two alternatives, “Watch · 2 min” captioned “How the machinery is engineered” (Fieldnote 101, which opens in a modal over the page; the recording keeps its own title inside the dialog) and “Listen · 2 min” (the brief plays in place); no episode list there. Then the three meanings of SPI, then one lesson index grouped “Level 100 · Foundations” (102 to 105), “The stack” (02), “Provider code and engineering” (04 to 06), “Across the path” (07), and “Working the stack” (08 to 12), 102 carrying the starting emphasis; a card shows its number or code, one title or question short enough to hold one line at desktop width, and a description only when it adds information. No doors, no trace invitation, no second introduction block, and no second index: the round-trip figure and the six-place ladder live on the Field guides page. The three meanings keep one order everywhere on Start (subhead, strip, cards, lessons): the stack, the interface inside each service, the engineering system; the card titles are of a length (“The Azure stack”, “The service interface”, “The engineering system”) so none wraps alone, and each card ends with its repository link at the bottom edge and carries no lesson link. Then Go deeper at the end, not collapsed: six entries in a quiet two-column list, one column on phones, separated by thin rules. Each entry keeps its uppercase repository or OSDU community kicker in the owner color, linked title, and one-line description. The entries cover the stack architecture, design guides, decision register, the engineering-system architecture, and the CIMPL and community partition references; the content lives in `chapters.start.deeper`, each entry naming a source key. The lessons’ “Go deeper in the documentation” accordion stays hidden on Start. The masthead carries no Explore link until Explore is a distinct view; Fieldnotes, Audio deep dives, and Visual field guides are three quiet icon links in the masthead, in that order, and appear nowhere else on Start (not in the rail, not repeated on the page); on a phone the masthead keeps the three icons and hides their labels from sight but not from screen readers, so nothing pushes the page wider than the screen.
- Headings and titles say what the thing is or does. A kicker above a heading exists only when it adds a category the heading lacks (“The word” above “SPI means three things here”, “Carry forward” above “What you can now say”, and “Documentation” above “Source documentation” do not). Copy does not describe the site's own method or repeat a sequence the index already shows (“Six views in order, then…”, “Each moment shows who acts and what changes”). Objects are named before they are referred to: a service change, an image digest, a temporary test deployment, not “the fix”, “that digest”, “the borrowed slot”. Prefer “How spi up builds the environment” to a formula, a count, or a contrast (“One command. Several kinds of work.”). Keep a short sentence when it is precise (“AKS is one part of the stack”). Misconception entries begin with the explanation; there is no scripted “Not quite.” Recording titles are the site's and say what the recording covers; the generated title stays in the episode's `origin` line.
- A component explanation answers the selected component in the running example's context first (what happens at runtime), then ownership, and its source link substantiates that claim (the provider class for provider behavior, the ADR for ownership). A poster shown beside a view says which example it follows when that differs from the running example.
- A recording is replaced from an approved script (see `docs/azure-spi-brief-script.md`), never by editing its transcript. The transcript represents the recording; corrections go in marker notes.

- The audio plays from one element in the page frame and never navigates on its own; switching episodes swaps the source. A marker’s timestamp and title seek the recording; the link beside it navigates, and copy never says a marker opens a lesson. Where the narration differs from the repositories, the marker carries a source-check note written to stand on its own: the summary states what is true, the note says what the recording said instead, and neither starts with “Source check” (the renderer adds that label). Marker titles and summaries name the subject plainly, without the recording’s metaphors or inventories of jargon. A learn view's `listen` cues point at markers, play in place, and are the only audio a map shows.

Fieldnotes are episodes with chapters keyed to claims: each claim, the running example, and the easy mistake is one chapter, titled with the claim headline, “Example: …” with the example's title, and “Easy mistake: …” with the myth's claim, so the video and the map use the same words. Lesson 07 has no map or claims to key to, so its Fieldnote's chapters are its themes, titled with the theme titles the page uses. Each lesson offers its own from “Watch this lesson”; Start offers Fieldnote 101 from its Introduction. A Fieldnote opens in the video modal: playback starts from the click that opened it, and a `?watch=` route opens it paused; captions and the source-check notes stay inside the player; chapter ticks over the seek area and the chapter list mark the chapter that is playing; focus stays in the dialog; closing (× or Escape) pauses the video, keeps the page position, and returns focus to the control that opened it. The dock pauses while the dialog is open, and the dock pauses the video. The enlarged poster fits the dialog until Zoom in is pressed (then it pans), and shows the origin and status line above the image. Profile layers say Included, Not deployed, or Provisioned in text, and the timeline's accessible name states the observed durations and that unmeasured positions are illustrative. No by-need index, no kicker, no premise, no scope note, no counts in headings, no method copy (how a guide was built, or an instruction to print). A poster carries one subject with a shape; a subject that is a list belongs in a native field guide. Every claim on a poster must trace to a design guide, decision record, or source file; cut what cannot be traced.
- A native field guide states one idea, names its sources, and links the view where it can be explored. Timing graphics label observations, ordered steps, continuing work, and deadlines separately.

## Beads Issue Tracker

This project uses **bd (beads)** for issue tracking. Run `bd prime` to see full workflow context and commands.

### Quick Reference

```bash
bd ready              # Find available work
bd show <id>          # View issue details
bd update <id> --claim  # Claim work
bd close <id>         # Complete work
```

### Rules

- Use `bd` for ALL task tracking — do NOT use TodoWrite, TaskCreate, or markdown TODO lists
- Run `bd prime` for detailed command reference and session close protocol
- Use `bd remember` for persistent knowledge — do NOT use MEMORY.md files

## Session Completion

**When ending a work session**, you MUST complete ALL steps below. Work is NOT complete until `git push` succeeds.

**MANDATORY WORKFLOW:**

1. **File issues for remaining work** - Create issues for anything that needs follow-up
2. **Run quality gates** (if code changed) - Tests, linters, builds
3. **Update issue status** - Close finished work, update in-progress items
4. **PUSH TO REMOTE** - This is MANDATORY:
   ```bash
   git pull --rebase
   git push
   git status  # MUST show "up to date with origin"
   ```
5. **Clean up** - Clear stashes, prune remote branches
6. **Verify** - All changes committed AND pushed
7. **Hand off** - Provide context for next session

**CRITICAL RULES:**

- Work is NOT complete until `git push` succeeds
- NEVER stop before pushing - that leaves work stranded locally
- NEVER say "ready to push when you are" - YOU must push
- If push fails, resolve and retry until it succeeds
